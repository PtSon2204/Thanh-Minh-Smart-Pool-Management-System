# Staff schedule state and transition rules

This note describes the current contract schedule, dated exception, and staff replacement transitions.
It is a code-maintenance reference, not a request to apply migrations or modify live data.

## Assignment state

| Current state | Action | Allowed transition | Guard |
|---|---|---|---|
| `Scheduled`, no attendance | Cancel | `Cancelled` | The assignment must still be scheduled when the update runs. |
| `Scheduled`, no attendance, future shift | Replace | Source becomes `Cancelled`; another employee gets the same date and shift | Preview and confirm checks below. |
| `Scheduled`, no attendance, today | Replace | Same as future replacement, only before the Vietnam shift start | Check the actual shift interval, including overnight end time. |
| `Scheduled`, no attendance | Move | Source becomes `Cancelled`; the same employee receives the selected shift on the same date | Source and destination must not have started; destination must not overlap or duplicate. |
| `Scheduled`, no attendance, generated by contract | Leave | All generated shifts for the selected date become `Cancelled` | Caller must provide every scheduled generated assignment for that date. Manual assignments are not cancelled. |
| `Present` or `Completed`, or attendance timestamps exist | Replace, move, or cancel | No transition | Attendance history is immutable through schedule edits. |
| `Cancelled` employee shift | Reuse same employee/date/shift tuple | Not allowed | Exact assignment tuples stay reserved as history. |

`StaffScheduleException` records preserve the source assignment IDs. A `Replace` exception also records its destination employee, which must reference an employee row. The source `EmployeeShift` stays in the database and retains its employee. A new replacement assignment points to the exception. When an eligible exact assignment already exists for the replacement employee, confirmation reuses it rather than creating a duplicate.

## Replacement proposal state

```text
not-started
   └─ Preview
        ├─ conflict ──> no token; no writes
        └─ ready ─────> preview token, expires after 15 minutes
                           ├─ source/target assignment state changes ──> stale; no writes
                           ├─ token expired or payload changed ──> stale; no writes
                           └─ Confirm ──> source cancelled, target assigned,
                                           assignment history and notifications saved
                                           in one transaction
                                               └─ operation receipt
                                                    └─ same operation ID + payload
                                                       returns same receipt
```

Contract and dated-exception previews can fail before returning a token. Since a preview does not apply schedule changes and has no operation ID, the UI reports the error and allows the administrator to retry. A confirmation with a lost response is different: keep its operation ID, lock edits, and query that receipt before allowing another action.

Confirmation locks both employee schedules, relevant schedule rows, and the operation ID. It reloads current rows and checks the preview hash before any write. A confirmed request with the same operation ID and proposal returns the original receipt. Reusing that ID with different proposal data is rejected.

## Replacement preview guards

The source must be `Scheduled`, unattended, and not started. The target must be a distinct, active, working employee with an allowed employment role. The shift must still be active. A target whole-day `Leave` blocks the assignment. The target must have no overlapping assignment. An exact target assignment is reusable only when it is also scheduled and unattended.

An existing `Move` or `Replace` exception for another source assignment does not block replacement. Exceptions are scoped by source assignment and shift slot, not by date alone. A day-level `Leave` suppresses remaining contract-generated shifts for that employee and date. Schedule regeneration suppresses replaced or moved source shifts and does not restore them.

## Confirmed transition defects and regression coverage

1. **Date-wide exception gate blocked independent edits.** `PlanException` rejected any second exception on the same date, even when it targeted a different assignment. The gate was removed. `StaffWorkPatternIntegrationTests.IndependentShiftMovesCanBeRecordedForTheSameDate` verifies two non-overlapping moves on one date. `StaffShiftReplacementIntegrationTests.ReplacementCanTargetAnotherShiftOnDateWithAnIndependentMoveException` verifies replacement alongside a separate move.
2. **Concurrent replay could miss the first receipt.** The replacement path checked receipts before acquiring schedule locks. Two confirmations could both pass that read. Confirmation now locks the operation ID and re-reads the receipt before planning. `StaffShiftReplacementIntegrationTests.ConcurrentConfirmationsWithOneOperationIdReturnTheSavedReceiptOnce` verifies one replacement and one set of deliveries for two contexts. `StaffShiftReplacementIntegrationTests.ConcurrentConfirmationsWithTheSameOperationIdReturnOneReceiptAndApplyOnce` checks that a changed payload under a saved operation ID returns `OPERATION_PAYLOAD_MISMATCH`.
3. **Replacement history could point to a missing employee.** The destination employee was stored without referential enforcement. A restrictive foreign key now protects the replacement history. `StaffShiftReplacementIntegrationTests.ReplacementHistoryRejectsANonexistentDestinationEmployee` verifies this in a fresh isolated PostgreSQL schema.
4. **Uncertain preview disabled its own recovery.** The shared mutation guard marked preview transport failures as uncertain, although previews have no operation ID. The “check result” action could not resolve a preview and the panel stayed locked. Preview failures now clear stale preview tokens and remain retryable; only confirmation failures require receipt recovery. A browser run with synthetic API responses verified a lost preview, successful retry, lost confirmation response, and successful receipt recovery.
5. **Replacement could cancel a concurrently checked-in shift.** The source assignment was tracked before its row lock. A check-in could commit while replacement waited, then tracking-query identity resolution reused the stale `Scheduled` entity. The replacement now locks the source row before its first tracked read. `ReplacementRejectsCheckInCommittedAfterPreviewAndBeforeSourceRowLock` coordinates the intervening check-in and verifies there is no cancellation.
6. **An expired mail lease could be overwritten by its old worker.** A slow sender could continue after lease expiry changed the row to `Unknown`, then save `Sent` or `Failed` from stale tracked state. The worker now renews before sending and writes results conditionally under the current lease ID. `ExpiredLeaseCannotBeOverwrittenByTheOriginalSendingWorker` forces the expiry during send and checks the row remains `Unknown`.
7. **Legacy invitations could fail approval after contracts became required.** The migration leaves prior `ContractJson` values null, but approval attempted to generate a schedule and threw `CONTRACT_REQUIRED`, rolling back approval. Legacy approvals now complete without schedule generation and return `skipped_legacy_no_contract`; new invitations still require contracts. `LegacyInvitationWithoutContractCanBeApprovedWithoutScheduleGeneration` covers this state.
8. **The state guide was ignored by Git.** The root ignore rules hid `docs/` and all Markdown, so normal staging would omit the guide. Precise exceptions now include this guide while keeping other documentation ignored.

## Adjacent staff onboarding, notification, and email-delivery states

| State | Action | Next state | Guard or retry rule |
|---|---|---|---|
| No invitation | Create | Invitation `PENDING`; revision `DRAFT` | Validate identity, role, join date, contract, profile, and uniqueness first. |
| `PENDING` invitation + `DRAFT` or `CHANGES_REQUESTED` revision | Resend | Invitation stays `PENDING`; token digest and expiry rotate | Old token becomes invalid; expiry is reset to 24 hours. |
| `PENDING` or `EXPIRED` invitation | Cancel | Invitation `CANCELLED`; non-approved revision `REJECTED` | Clear token/password state and queue document cleanup. |
| `DRAFT` or `CHANGES_REQUESTED` revision | Save draft | Revision `DRAFT`, version increments | Validate the editable profile. |
| Editable revision | Submit | Revision `SUBMITTED`, version increments | Validate profile, password, contact/identity uniqueness, and claims. |
| `SUBMITTED` revision | Approve, request changes, or reject | `APPROVED`, `CHANGES_REQUESTED`, or `REJECTED` | Approval requires explicit confirmation; repeating an already completed approval does not regenerate the schedule. |
| Correction `REQUESTED` | Open correction | Correction `OPENED`; new draft revision | Only one active correction request exists per employee. |
| Correction `OPENED` | Submit corrected profile | Revision `SUBMITTED`; correction stays `OPENED` | Same submission validation and uniqueness checks apply. |
| Correction revision `SUBMITTED` | Approve or reject | Correction `CLOSED` | Review action closes the correction after the revision decision. |
| Legacy pending invitation without `ContractJson` | Approve | Invitation and revision complete; schedule is explicitly skipped | New invitations still require a contract. |
| Recipient notification unread | Mark read | Same notification becomes read | The update matches both notification ID and authenticated recipient ID. |
| Email delivery `Pending` or due `Failed` | Worker claims | `Sending` with a two-minute lease | Worker claims at most 20 rows, skips rows locked by another worker, and retries only while attempts are below three. |
| `Sending` | Send succeeds | `Sent` | Clear lease and prior error. |
| `Sending` | Send fails | `Failed` | Retry with backoff while attempts remain; invalid recipient email is terminal at attempt three. |
| `Sending` lease expires | Worker recovers | `Unknown` | Record `DELIVERY_RESULT_UNKNOWN`; the worker does not retry `Unknown` automatically. |

The worker renews a lease before each send and saves a result only while the row remains `Sending` under that worker's lease ID.

Pool-duty workflow states are excluded from this audit. This table covers invitation delivery and recipient notifications only.

## Validation boundary

The focused work-pattern/replacement filter passed 25 cases against isolated PostgreSQL. The final targeted filter `FullyQualifiedName~ReplacementRejectsCheckInCommittedAfterPreviewAndBeforeSourceRowLock|FullyQualifiedName~ExpiredLeaseCannotBeOverwrittenByTheOriginalSendingWorker|FullyQualifiedName~LegacyInvitationWithoutContractCanBeApprovedWithoutScheduleGeneration` passed all 3 added regressions. Migration upgrade/rollback SQL generation passed. One browser run used synthetic API responses to verify preview retry and receipt recovery. No broad suite ran. Do not apply the migration to a shared or business database.

**DO NOT EVER OVERTEST IN ANY WAY, SHAPE, OR FORM.**
